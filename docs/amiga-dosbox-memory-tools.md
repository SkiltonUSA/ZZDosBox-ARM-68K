# ZZDosBox Developer memory tools

Version **0.12.0-dev**, validated on the physical A4000TX/ZZ9000 and installed
as the separate **ZZDosBox-Developer** launcher with **ZZDosBox-Memory** runtime.
Experimental **guest PC RAM** tools in the MUI Developer tab. The normal
emulator remains a separate build. These tools do not access Amiga memory,
ZZ9000 firmware, or arbitrary ARM addresses.

Enable **Memory tools**, choose Direct rendering and launch a program or DOS
terminal. The launcher remains responsive during this developer session.
A Workbench window keeps the controls visible alongside DOS.

- **Monitor:** hex/ASCII view at a guest physical address; optional automatic
  refresh, 8/16/32-bit little-endian edits, and one-level undo.
- **Scanner:** exact or unknown initial value; refine by equal, changed,
  unchanged, increased or decreased. Results select an address for viewing or
  editing. Comparisons are unsigned integers.
- **Disassembler:** DOSBox's x86 decoder with explicit 16/32-bit mode, operating
  on the same bounded memory snapshot. It is not an ARM instruction debugger.
- **Pause / Resume / Stop:** cooperative control outside execution of translated
  x86 code. Edits and scans require pause; reads can capture a consistent page
  at an execution boundary while the guest runs.

Addresses are hexadecimal, values accept decimal or a `0x` prefix. An edit
compares the displayed old value before writing; refresh if that value changed.
Undo also checks the current value. Edits affect the running guest only, not a
saved patch or a disk image.

## Bounds and implementation

Reads are at most 256 bytes. Scans cover at most 64 KiB and retain at most 4096
matches. An overflowing scan is rejected; narrow the range before refining.
Unaligned words/dwords are included. The legacy `A0000–FFFFF` video/ROM hole,
addresses beyond the configured RAM and wrapping spans are rejected. Addresses
are **physical**, not protected-mode virtual addresses or segment:offset pairs.
Disassembly uses the displayed address as its origin; it does not resolve
segment descriptors, virtual-page mappings or segment-boundary wrapping.

The 68k UI sends a fixed-size Exec message to the developer runtime. The
runtime copies it into a bounded command/reply region within the existing
Exec-owned allocation. Core1 handles it outside the x86 decoder and returns a
snapshot. The ordinary runtime has no memory command polling. Editing a page
containing translated code goes through DOSBox's code-page write handler, which
invalidates affected translations. Cancellation remains serviced while paused.

The disassembler comes from the pinned libretro DOSBox revision recorded in
`amiga/dosbox/developer/vendor/upstream.json`. Original notices are retained.
The adaptation limits instructions to 15 bytes, bounds output, handles truncated
snapshots, and fixes template-terminator and segment-register bounds bugs found
by randomized tests. It does not enable the upstream interactive debugger or
instruction stepping.

## Build and verification

Build the standard Direct/VFP flags with `--pc-memory-debug` for the isolated
runtime; install it beside the developer launcher under `ZZDosBox-Memory`.
`scripts/build_dosbox_launcher.py` builds the MUI interface and bounded decoder.
Memory tools currently exclude OpenGL and simultaneous video-trace/frame
breakpoint builds. These are development tools and affect performance.

Native sanitizer tests cover memory ranges, compare-before-write, unsigned
scan/refine logic, overflow and paging of results. Decoder checks cover both
instruction modes, truncated instructions, repeated prefixes and 100,000 random
snapshots. Linked ARM and physical validation results are recorded separately;
a compiled UI alone does not establish a successful hardware session.

Physical checks passed the memory command protocol, paused writes/refinement,
stale-value and excluded-address rejection, and external editing of translated
x86 code. The MUI session separately verified byte editing, an exact scan result,
16/32-bit disassembly, undo to the original byte, live monitoring, Resume and
Stop. All three sessions restored the checked ARM/SIMD/cache state and released
owned memory. The normal launcher and runtime checksums remained unchanged.
An installed-path protocol smoke test passed after transfer verification.
Screenshots, closed logs and the exact installed executables are retained in
[`amiga/records/2026-10-14/dosbox-memory`](../amiga/records/2026-10-14/dosbox-memory).

The linked ARM model suite is `tests/amiga/dosbox/check_memory_arm.py --build
<developer-build-directory>`. It exercises command acknowledgements, paused
edits/scans, cancellation both while paused and during a framebuffer copy, and
editing already translated x86 instructions. The original `MEMPATCH.COM`
fixture is generated by `scripts/make_dosbox_memory_fixture.py`; it exits only
after executing the replacement instruction. No commercial game is required
for these checks.
